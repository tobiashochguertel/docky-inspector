Anatomy of a Docky dock ← back to inspector

Everything lives in a fixed nesting. This page walks it outermost → innermost: the bar, then sections, then tiles, then what is inside a tile. The figures are symbolic — they name parts and relationships, never numbers. Each section can show the real numbers measured from your running Docky; expand live values wherever you want them. Every box is drawn to true scale at 2.5 px/pt.

1 · The bar — the outermost container

level 1

  • The bar is the only element that touches the screen. Everything else is inside it: the dashed content box is the tiles, and everything between that box and the bar edge is padding.
  • Width (x) follows the content: width = n·w + (n−1)·s + k·d + 2p — n tiles of width w, n−1 gaps of spacing s, k dividers of width d, padding p at both ends. Divider width d and a non-zero s are terms in the sum even when they are zero today.
  • Height (y) follows the tile, not the content: height = h + 2p, because every tile has the same height h. There is no n in this formula — adding a tile never changes the bar's height.
  • So: width scales with the number of tiles, height with their size. Pin an app and the bar widens; change the icon size and every tile plus the bar grow together.
  • The bar owns no visuals of its own — background and separation only.

2 · Sections — runs of tiles

level 2, inside the bar

  • A section is a run of tile kinds: pinned apps, app folders, minimized windows, trash. The inspector marks each run under the bar.
  • A divider separates two sections. It is not a tile — no frame, no icon, no label row, and it takes no part in row alignment. It contributes its width d to the bar's width (§1) and nothing else.
  • Sections exist only at bar level. A tile knows nothing about them; adding or removing a divider never moves a tile vertically.

3 · Tiles — one slot per item

level 3, inside a section

  • Every tile reserves the same frame w × h, whatever it shows. That uniformity is the whole reason the rows stay aligned — a folder tile and an app tile occupy exactly the same box.
  • Frames never overlap. Centre-to-centre distance is (w₁+w₂)/2 + s; with equal widths that is w + s, so the row advances by one frame plus one spacing per tile.
  • Height is composed from top to bottom: h = 2p + i + l — padding p at the top, the icon i, the reserved label row l = g + text, then padding p again at the very bottom. The second p is below the label, not below the icon; the gap between icon and label is g, which lives inside l. Measured on a live app tile: 8 + 40 + 2 + 10 + 8 = 68. With labels off only 2p + i remains, which is why a label adds exactly one row and never re-pads anything above it.
  • The running indicator below the icon is an optional overlay — a dot for one window, a pill for several. It is drawn outside the icon slot and takes no layout space, so switching it on or off cannot move anything.

4 · Inside one tile — outer ring to painted pixels

level 4, inside a tile

Two tile kinds, drawn separately. Both stacks come from the frames Docky measured for a live tile, so the bands are what the layout actually produced rather than what the layout code implies. Each figure's D2 source is shown underneath.

  • Tile frame — the reserved box. It has no visuals, only space.
  • Padding — p at the top of the frame and again at the very bottom, below the label row, plus iconPad horizontally inside the frame. Empty space, never painted. The bottom band is easy to miss because nothing is drawn there, which is why the bands in the figures are read from Docky's own measurements rather than inferred from the layout code.
  • Icon slot — the icon's layout box. Its width depends on the tile kind, which is why the two tiles below differ: an app tile insets only by iconPad, so i = w − 2·iconPad and with the default of 0 the slot spans the frame; a widget chrome tile also reserves the fixed chromeInset on all four sides, so content box = w − 2·(chrome + iconPad) and the slot stops short of every edge. The top drawing is your current app tile, the bottom one the widget variant.
  • Painted artwork — what is drawn inside the slot. For an app icon it fills the slot and the perceived gap comes from its transparency; for folders and minimized cards the painted box is smaller (§6).
  • Label row — one reservation l = g + ceil(font × 1.2): the fixed gap g above the text, then the text itself. Identical on every tile, which is what keeps the rows aligned. The text is clipped to the box inset sideInset per side, so long names truncate instead of touching neighbours.
  • Overlays — running indicator and notification badge float above the tile and take no layout space.

4b · The label row, magnified — and where it can sit

level 4 · zoomed out from §4, then the four placements

  • Zoomed, the label row resolves into three parts: the fixed gap g, the text, and the sideInset kept on each side of the text. The inset is why two long names truncate instead of running into each other even at zero tile spacing.
  • The text height comes from the font size — ceil(font × 1.2) — and l = g + text is identical on every tile, which is what keeps the rows aligned.
  • Placement only decides where the row goes, never its size. Below and above keep the tile's width at w and add the row's height; leading and trailing add the row's width instead, so those tiles become wider than they are tall — capped by the fixed maxSidewaysLabelWidth so one long name cannot stretch the dock.

6 · Tile variants — same frame, different artwork

level 3, one card per kind

  • App folder — the material background hugs the 2×2 mosaic instead of the slot, with a chrome margin of folderChromeFraction of the smaller side, so folders keep the breathing room that transparency gives app icons. Stack mode fans full-size icons instead.
  • Minimized window — a preview card at cardHeightScale of the slot plus the owning app's badge at badgeScale; without screen-recording permission the card falls back to a placeholder in the same slot.
  • Launchpad / Start Menu — ordinary app tiles pointed at a fixed bundle id with an overridable icon.
  • Widget — keeps the label row so rows stay aligned, but never draws a label.
  • Spacer — no label row at all; it is a gap, not a tile that shows something.

7 · Reading the inspector

level 3 · tools

Guides — tile top, icon bottom, label baseline ≈, tile bottom. If all four run unbroken across the bar, the rows are aligned.

slot vs painted — slot (green dashed) is the measured layout box, painted (sand) the measured visual. Equal for app icons; smaller for mosaics and cards. That difference is the optical gap story.

  • Metrics modal — Box = the tile in the bar, Icon/Title = sub-boxes with their margins to the tile edge, Gaps = the margin visual alone.
  • Section markers under the bar are level 2, guides level 3, the modal's sub-boxes level 4 — the same structure at three zoom levels.
